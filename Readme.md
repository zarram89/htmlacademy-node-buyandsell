# REST API «Куплю-продам»

### Техническое задание
Проект «Куплю. Продам»
«Куплю. Продам» — сервис объявлений. Здесь покупают и продают любые вещи. Вся необходимая информация для покупки представлена в карточке продаваемого предмета. Зарегистрированные пользователи могут обсуждать объявления при помощи комментариев.

1. Задача
1.1. Разработать сервис для проекта «Куплю. Продам».

1.2. Сервис предоставляет REST API интерфейс и CLI интерфейс.

1.3. Соединить бэкенд (сервис) с фронтендом (дополнительное задание).

2. Сценарии
2.1. Создание нового объявления.

2.2. Редактирование объявления.

2.3. Удаление объявления.

2.4. Получение списка категорий.

2.5. Получение списка объявлений определённой категории.

2.6. Получение списка новых объявлений.

2.7. Получение списка обсуждаемых объявлений.

2.8. Получение детальной информации по объявлению.

2.9. Получение списка комментариев для объявления.

2.10. Добавление комментария для объявления.

2.11. Создание нового пользователя.

2.12. Вход в закрытую часть приложения.

2.13. Выход из закрытой части приложения.

2.14. Проверка состояния пользователя.

3. Сущности
3.1. Пользователь
3.1.1. Пользователь представлен набором информации:

Имя. Обязательное. Мин. длина 1 символ, макс. длина 15 символов;
Фамилия. Обязательное. Мин. длина 1 символ, макс. длина 15 символов;
Электронная почта. Обязательное. Валидный адрес электронной почты;
Аватар пользователя. Необязательное. Изображение пользователя в формате .jpg или .png;
Пароль. Обязательное. Мин. длина 6 символов, макс. длина 12 символов.
3.1.2. В приложении не может быть двух пользователей с одинаковым email.

3.2. Категория
3.2.1. Категория представлена набором информации:

Название категории. Обязательное. Мин. длина 3 символа, макс. длина 12 символов;
Изображение для категории. Обязательное. Путь к изображению.
Количество объявлений. Рассчитывается автоматически.
3.2.2. Список категорий предопределён: «Дом», «Электроника», «Одежда», «Книги», «Спорт» и «Авто».

3.3. Объявление
3.3.1. Объявление представлено набором информации:

Наименование. Обязательное. Мин. длина 10 символов, макс. длина 100;
Описание объявления. Обязательное. Мин. длина 20 символов, макс. длина 1024 символа;
Дата публикации объявления. Обязательное. Дата публикации, обязательно для заполнения. По умолчанию — текущая дата;
Фотография. Обязательное. Формат: *.jpg, *.png;
Тип объявления. Обязательное. Один из вариантов: «Куплю» или «Продам»;
Количество комментариев. Рассчитывается автоматически.
Стоимость. Обязательное. Мин. 100, Макс. 200 000;
Автор объявления. Обязательное. Ссылка на сущность «Пользователь».
Категории. Обязательное. Ссылка на сущность «Категория». Объявление может принадлежать к нескольким категориям.
3.4. Комментарий
3.4.1. Комментарий представлен набором информации:

Текст комментария. Обязательное. Мин. длина 5 символов, макс. длина 1024 символа;
Автор комментария. Обязательное. Ссылка на сущность «Пользователь».
4. Функциональность
4.1. Command Line Interface
4.1.1. Приложение предоставляет Command Line Interface (CLI). Для запуска CLI предусмотрен отдельный сценарий в package.json — cli.

4.1.2. Модуль, отвечающий за запуск CLI, содержит корректный shebang.

4.1.3. CLI поддерживает обработку аргументов:

--version. Выводит информацию о версии приложения. Информация о версии считывается из package.json. Пример вывода: 1.0.1;
--help. Выводит список и описание всех поддерживаемых аргументов. Оформление списка остаётся на усмотрение студента. Пример оформления продемонстрирован на рисунке 1.
--generate <n> <filepath> <url>. Создаёт файл в формате tsv с тестовыми данными. Параметр n задаёт количество генерируемых объявлений. Параметр filepath указывает путь для сохранения файла с объявлениями. Параметр <url> задаёт адрес сервера, с которого необходимо взять данные. Пример файла доступен в репозитории, в директории examples. Информация об объявлении включает сведения о пользователе. Список полей объявления и пользователя представлен в разделе с описанием сущностей.
--import <filepath>. Импортирует в базу данных информацию из tsv-файла. Путь к файлу передаётся в параметре filepath.
4.1.4. Запуск CLI без аргументов приводит к исполнению команды --help.

4.2. REST API в формате OpenAPI
4.2.1. Приложение предоставляет REST API интерфейс. Имена ресурсов, маршрутов остаются на усмотрение студента.

4.2.2. Спецификация REST API представлена в формате OpenAPI.

4.2.3. Для описания спецификации используется язык YAML.

4.2.4. Спецификация сохранена в директории specification (в корне проекта).

4.3. REST API сервис
4.3.1. Сервис предоставляет ресурсы в соответствии со спецификацией.

4.3.2. Настройки, необходимые для запуска и работы сервиса передаются с помощью переменных окружения.

4.3.3. Список всех переменных окружения приведён в файле Workflow.md, который расположен в корне проекта. Формат описания: PARAM=value — описание.

4.3.4. Для удобства передачи параметров окружения используются .env-файлы. Они не должны сохраняться в системе контроля версий.

4.3.5. В корне проекта расположен .env.example. Он содержит список всех переменных окружения, необходимых для работы приложения. Переменным заданы значения по умолчанию (для примера использования).

4.4. Запуск сервиса
4.4.1. При старте сервис проверяет список установленных переменных окружения. Если какая-то переменная не задана, сервис выдаёт сообщение об ошибке и прекращает выполнение.

4.4.2. В файле Workflow.md предусмотрите раздел «Запуск проекта» и опишите в нём подробную инструкцию по запуску проекта.

4.4.3. В файле Workflow.md в секции «Сценарии» перечислите все сценарии, доступные в package.json и опишите их предназначение.

В корневой директории проекта расположен файл docker-compose.yml для быстрого разворачивания базы данных MongoDB с помощью Docker (если вы используете в работе docker).

5. Список ресурсов
5.1. Создание нового объявления
5.1.1. Сервис предоставляет ресурс для создания новых объявлений.

5.1.2. Создавать объявления могут только авторизованные клиенты.

5.1.3. Для создания нового объявления клиент передаёт информацию, указанную в пункте 3.3, за исключением значений, которые рассчитываются автоматически.

5.1.4. Перед созданием объявления данные, полученные от клиента, валидируются. Если валидация не пройдена, сервис возвращает ошибку и корректный код состояния. Объявление при этом не создаётся.

5.1.5. В случае успешного создания объявления, сервис в ответе возвращает информацию о созданном объявлении (объект объявления).

5.2. Редактирование объявления
5.2.1. Сервис предоставляет ресурс для редактирования объявлений.

5.2.2. Клиент может редактировать только свои объявления.

5.2.3. При попытке отредактировать чужое объявление, сервис возвращает ошибку и корректный код состояния.

5.2.4. Для редактирования объявления клиент передаёт обновлённую информацию по объявлению (кроме значений, которые рассчитываются автоматически), перечисленную в пункте 3.3 и идентификатор редактируемого объявления.

5.2.5. Полученные данные проходят валидацию. Если валидация не пройдена, сервис возвращает информацию об ошибке и корректный код состояния.

5.2.6. В случае успешного обновления объявления, сервис возвращает клиенту обновлённый объект объявления.

5.2.7. Редактировать объявления могут только авторизованные клиенты.

5.3. Удаление объявления
5.3.1. Сервис предоставляет ресурс для удаления объявлений. Клиент может удалять только свои объявления.

5.3.2. При попытке клиентом удалить объявление другого пользователя, сервис возвращает ошибку и корректный код состояния.

5.3.3. При удалении объявления, комментарии к объявлению удаляются автоматически.

5.3.4. Удалять объявления могут только авторизованные клиенты.

5.4. Список категорий
5.4.1. Сервис умеет возвращать информацию о категориях для объявлений.

5.4.2. Сервис всегда возвращает информацию о шести категориях.

5.4.3. Каждая категория в списке представлена набором информации, указанным в пункте 3.2.

5.4.4. Создание новых категорий не предусмотрено.

5.5. Список объявлений из определённой категории
5.5.1. По умолчанию сервис возвращает не больше 25 объявлений из определённой категории.

5.5.2. Клиент может запросить больше объявлений за раз, указав нужное количество в параметре запроса.

5.5.3. Сервис всегда возвращает отсортированный список объявлений по дате публикации (по убыванию).

5.5.4. Объявление не содержит список комментариев. Только информацию о их количестве. Для запроса комментариев к определённому объявлению сервис предоставляет отдельный ресурс.

5.5.5. Список объявлений из определённой категории могут запрашивать анонимные и авторизованные клиенты.

5.6. Список новых объявлений
5.6.1. Сервис предоставляет ресурс для получения списка новых объявлений. Новые объявления определяются по дате публикации.

5.6.2. Сервис возвращает отсортированный список объявлений по дате публикации (по убыванию).

5.6.3. Список новых объявлений могут запрашивать авторизованные и анонимные клиенты.

5.7. Список обсуждаемых объявлений
5.7.1. Сервис предоставляет ресурс для получения списка обсуждаемых объявлений. Ресурс возвращает не больше 5 объявлений.

5.7.2. Под обсуждаемыми объявлениями подразумеваются объявления с наибольшим количеством комментариев.

5.7.3. Сервис возвращает отсортированный список объявлений по количеству комментариев. Список отсортирован по убыванию (сначала объявления с наибольшим количеством комментариев).

5.7.4. Список обсуждаемых объявлений могут запрашивать авторизованные и анонимные клиенты.

5.8. Детальная информация по объявлению
5.8.1. Сервис предоставляет ресурс для получения детальной информации по одному объявлению.

5.8.2. Информация по объявлению содержит все поля перечисленные в пункте 3.3.

5.8.3. Детальная информация по объявлению включает сведения о количестве комментариев, но сами комментарии не включены.

5.8.4. Детальную информацию по объявлению могут запрашивать авторизованные и анонимные клиенты.

5.9. Список комментариев для объявления
5.9.1. Сервис предоставляет ресурс для получения списка комментариев для определённого объявления.

5.9.2. Сервис всегда возвращает список из 50 (или меньше) последних комментариев.

5.9.3. Комментарии отсортированы по дате публикации (по убыванию). Сначала новые, потом старые.

5.9.4. Комментарий в списке представлен набором информации перечисленной в пункте 3.4.

5.9.5. Комментарии могут запрашивать авторизованные и анонимные клиенты.

5.10. Добавление комментария
5.10.1. Сервис предоставляет ресурс для добавления комментариев к определённому объявлению.

5.10.2. Добавлять комментарии могут только авторизованные клиенты.

5.10.3. Для добавления нового комментария к объявлению, клиент передаёт набор информации, указанный в пункте 3.4 и идентификатор объявления, для которого создаётся комментарий.

5.10.4. Перед добавлением комментария, сервис валидирует данные. В случае ошибки валидации, сервис возвращает ошибку и корректный код состояния.

5.10.5. В случае успешного добавления комментария, сервис возвращает информацию о созданном комментарии (объект комментария).

5.10.6. Удаление и редактирование комментариев не предусмотрено.

5.11. Создание нового пользователя
5.11.1. Сервис предоставляет ресурс для создания нового пользователя.

5.11.2. Для создания нового пользователя клиент отправляет запрос и передаёт данные, указанные в пункте 3.1.

5.11.3. Создавать новых пользователей могут авторизованные и анонимные клиенты.

5.11.4. Email создаваемого пользователя уникальный. В системе не может быть двух пользователей с одинаковым email.

5.11.5. Данные, полученные от клиента проходят валидацию. Если проверка не пройдена, сервер возвращает ошибку и корректный код состояния.

5.11.6. В случае успешного создания пользователя, сервис возвращает информацию о созданном пользователе (объект пользователя). Возвращаемая информация не содержит конфиденциальных данных.

5.11.7. Пароль пользователя не хранится в базе данных в открытом виде. Вместо этого хранится хеш пароля.

5.12. Вход в закрытую часть приложения
5.12.1. Сервис предоставляет ресурс для аутентификации и авторизации пользователя.

5.12.2. Для входа в закрытую часть приложения клиент передаёт логин (email) и пароль пользователя.

5.12.3. Если логин или пароль неверный, или пользователь не существует, сервер возвращает ошибку и соответствующий код состояния.

5.12.4. В случае успешной проверки логина и пароля, сервис возвращает клиенту токен.

5.12.5. Клиент использует этот токен для отправки любых запросов. Токен передаётся в заголовках.

5.13 Завершение сеанса (только если используются сессии)
5.13.1. Сервис предоставляет ресурс для завершения пользовательского сеанса.

5.13.2. Ресурс доступен только авторизованным клиентам.

5.13.3. Если токен прошёл проверку, сервис завершает пользовательский сеанс (сессию). В противном случае, возвращает ошибку и соответствующий код состояния.

5.14 Проверка состояния клиента
5.14.1. Сервис предоставляет ресурс для проверки состояния клиента — авторизован или нет.

5.14.2. Проверка состояния клиента производится на основании сессионного токена.

5.14.3. Если клиент авторизован, сервис возвращает соответствующий код состояния и информацию о пользователе (смотри пункт 3.1). Информация о пользователе не должна содержать конфиденциальные данные (пароль).

6. Валидация
6.1. Данные, полученные от клиента проверяются перед использованием (приводятся к нужному типу, проверяются идентификаторы для связанных сущностей и так далее).

6.2. Данные, которые не удовлетворяют правилам валидации не могут использоваться для создания или редактирования сущностей. В таких ситуациях сервис возвращает ошибку и соответствующий код состояния.

7. Ошибки
7.1. В случае невозможности выполнения запроса, сервис возвращает клиенту список ошибок. Ответ с ошибкой содержит описание ошибки и соответствующий код состояния.

7.2. Формат описания ошибок и их детализация остаются на усмотрение студента.

8. Фронтенд (необязательное задание)
8.1. Фронтенд для работы с сервисом предоставляется в виде готового приложения.

8.2. В readme.md к фронтенду приводится описание ресурсов к которым обращается приложение.

8.3. Студент самостоятельно обновляет во фронтенде список маршрутов и при необходимости корректирует структуры данных.

8.4. Допускается внесение любых изменений во фронтенд.

9. Технические требования
9.1. Проект запускается и работает в актуальной версии Node.js.

9.2. Для разработки проекта используется TypeScript.

9.3. Для хранения данных используется MongoDB.

9.4. Для обработки запросов от клиентов используется Express.js.

9.5. Для работы с большими файлами (или файлами, которые потенциально могут стать большими) используются потоки (Streams).

9.6. В коде не должно быть зашито данных, которые могут меняться при переносе в продуктовую среду. Например: доступы для подключения к СУБД, адрес сервера для получения тестовых данных и так далее. Все перечисленные данные должны устанавливаться через переменные окружения.

9.7. Замена пакетов, не перечисленных в технических требованиях — допускается по согласованию с наставником.
